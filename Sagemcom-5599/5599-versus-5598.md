# Sagemcom 5599 vs 5598 — API comparison

Based on two HAR captures, compared against the HAR captures and
`Sagemcom5598-api.md` one directory up:

- `sagemcom-5599-initial.har` — login → dashboard → wifi pages (2.4/5/6GHz) →
  mesh topology → hosts/DHCP page → logout (121 entries, 53 `/api/` calls).
- `sagemcom-5599-firewall.har` — login → dashboard → firewall page (security
  level + Custom/Low/Medium/High chains) → hosts/DHCP/NAT/UPnP/portblacklist
  page → add one custom firewall rule → enable the Custom chain → advanced
  UPnP/ping-respond page → logout (128 entries, 61 `/api/` calls).

Between the two, MLO and `wan/ip/stats` still weren't visited — their absence
here doesn't mean they're gone on the 5599, just unconfirmed.

## Device identity

| | 5598 | 5599 |
|---|---|---|
| `productClass` | `F5598T` | `FAST5599` (inconsistent naming style between firmwares) |
| Serial | `N725115C6000105` | `N726021DE000005` |
| Hardware version | — | `1.1` |
| CPU | — | ARM (ARMv8 Processor rev 0), kernel `4.19.294` |
| External firmware | `SGQA530011400P` | `SGNA530000800` |
| Internal firmware | `sw25.2.36` | `sw25.2.25` |

Same `sw25.2.x` build family, different branch/branding. Bundled UI assets on
the 5599 include `logo_bezeq.svg`, suggesting an Israeli-market build vs. the
5598's Delta Fiber (NL) one.

## Unchanged

- **Login flow is byte-for-byte identical**: `POST /api/v2/login-params` →
  `{salt, nonce}`, then `POST /api/v1/login` with `login`/`auth_key`/`cnonce`,
  same SHA-512-crypt + SHA-512-hex chaining. `sagemcom5598.py`'s auth code
  should work unmodified against a 5599.
- `/api/v1/open`, `/api/v2/home`, `/api/v1/wan/ipv4`, `/api/v1/wan/status`,
  `/api/v1/device/features`, `/api/v1/user`, `/api/v1/session-count`,
  `/api/v1/session-timeout`, `/api/v1/voice/info`, `/api/v1/voice/v1/lines`,
  `/api/v1/dhcp`, `/api/v1/wireless/bandsteering` — same JSON shape as 5598.
- `/api/v4/easymesh/meshdevices` — same nested structure (`wifiRadios` →
  `ssids` → `stations`, `ethernetPorts`).
- Same REST server banner (`Server: Sagemcom Rest`), same `[{...}]`
  array-wrapping convention almost everywhere.

## Changed

- `GET /api/v1/ui/language` returns **200** (empty `language`/
  `available_languages`) instead of 5598's constant 400 — and correctly
  **401** once logged out, which is a useful new data point (the 5598 docs
  didn't note the unauthenticated status code).
- `/api/v2/wireless/{band}` (`24`/`5`/`6`) has **no `/stats/` segment** and is
  a completely different payload than 5598's `/api/v2/wireless/stats/{band}`:
  it's the full radio/SSID config (channel, standard, security protocol,
  **plaintext passphrase**, TxPower, htbw, WPS state) rather than traffic
  counters. Whether the 5599 still has a separate `/stats/` endpoint for
  rx/tx byte counters wasn't exercised in this capture — worth checking
  directly against the router.

## New endpoints

Not present in any of the 5598 HARs (confirmed by grepping all 8 capture
files):

- `GET /api/v1/deviceInfo` — a big "everything" dashboard object:
  serial/model/MACs, CPU/memory/flash stats, kernel/arch, WAN + LAN
  IPv4/IPv6, NAT session counts, **and** a per-band wireless summary with
  SSID/status/security (no passphrase here, unlike `/api/v2/home`).
- `GET /api/v1/dhcp/clients` — separate from `/api/v1/dhcp`; returned empty
  `{"dhcp":{"clients":[]}}` in this capture.
- `GET /api/v1/dhcp/leases` — active lease list (`id`, `hostname`,
  `ipaddress`, `macaddress`, `expiresIn`). **Note:** this is the one
  endpoint that breaks the array-wrapping convention — the response is a
  bare object, not `[{...}]`.
- `GET /api/v1/lan/ipv6` — router's own LAN IPv6 address + link-local
  address.
- `GET /api/v1/wireless/ssid_status` — flat list of every SSID
  (Primary/Guest/Backhaul × 2.4/5/6GHz) with up/down status, simpler than
  parsing `/api/v2/home`.
- `GET /api/v1/parental_control` — schedule list keyed by `SourceMac`, each
  with `enable`, `AlwaysBlock`, and a `timeslots` array. Not present in any
  5598 HAR (feature flag for it does exist on both — `device/features` lists
  `parental_control: enable: true` — but the endpoint itself was never
  exercised in the 5598 captures).
- `GET /api/v1/firewall/pingrespond` — `{"firewall":{"pingrespond":{"enable":true}}}`,
  i.e. whether the router answers WAN pings. Not in any 5598 HAR.
- `GET /api/v1/advanced/upnp` — `{"UPNPEnable": false}`. This is a **second,
  separate** UPnP toggle alongside the pre-existing `/api/v1/upnp/igd` (which
  is unchanged from 5598 — same `state`/`enable`/`uuid`/`adv_interval`/`adv_ttl`
  shape). Not clear yet whether these two ever disagree or which one the UI
  treats as authoritative.

## Firewall / NAT / UPnP details (`sagemcom-5599-firewall.har`)

- `GET /api/v2/firewall`, `/api/v1/nat/rules`, `/api/v1/upnp/igd`,
  `/api/v1/firewall/portblacklist`, `/api/v1/dhcp` — all **unchanged** from
  the 5598 shapes described in `Sagemcom5598-api.md`.
- `/api/v2/firewall/chain` supports four named chains — `Low`, `Medium`,
  `High`, `Custom` — each with its own `default_policy` and `rules` list.
  The three preset chains (Low/Medium/High) ship with predefined rules
  (`Targetchain` forwarding rules plus per-service `Accept`/`Drop` rules,
  e.g. High allow-lists HTTP/HTTPS/FTP/SSH/IMAP/etc. by name, Medium drops
  NETBIOS and isolates the guest bridge). **This is not actually new** — the
  same four chains exist in the 5598's own
  `192.168.1.254-new-login-and-firewall-and-portforwarding.har`, just never
  written up in `Sagemcom5598-api.md`, which only documents `Custom`.
- **Newly observed (not captured in any 5598 HAR, though very likely present
  there too given the identical response shape):**
  - `PUT /api/v2/firewall` — form body `level=<n>` — sets the overall
    firewall security level (the same `level` field `GET /api/v2/firewall`
    returns, e.g. `2`).
  - `PUT /api/v2/firewall/chain` — form body `chain=<name>&enable=<bool>` —
    enables/disables a chain. **Important:** adding a rule via
    `POST /api/v2/firewall/chain/rules` does **not** implicitly enable the
    chain it was added to — the UI had to separately `PUT` `chain=Custom&
    enable=true` after posting the rule, since the Custom chain came back
    `"enable": false` on the preceding `GET`.
- The manually-added custom rule (via the general "add rule" form, not the
  quick ipv6-port-open action) posts the **same field set** documented for
  5598's `POST /api/v2/firewall/chain/rules` (`chain`, `enable`, `action`,
  `description`, `service`, `protocol`, `src_ports`/`dst_ports`,
  `src_port_range_max`/`dst_port_range_max`, `src_intf`/`dst_intf`,
  `ip_protocol`, `order`) — confirms that field set is the general form
  schema, not something specific to the ipv6-port quick action. This capture
  used `protocol=tcp` (single protocol, not `tcp,udp`) and `order=1` (not the
  quick action's hardcoded `6`), posted twice (`lan`→`wan` then `wan`→`lan`)
  exactly like the 5598's ipv6-port-allow pattern.

## Other notable differences

- `/api/v1/hosts` entries are richer on the 5599: wireless clients get a
  nested `wireless` object (`mcs`/`rate`/`rssi0`/`band`) and wired clients
  get a mirroring nested `ethernet` object (`speed`, `port` — e.g. `"LAN4"`,
  a named port rather than a numeric index); both also add `lastseen`,
  `interface_l3`, and `location` fields not documented for the 5598.
- The frontend is a different Angular build entirely (different JS chunk
  hashes/filenames vs. the 5598's), so this isn't just a firmware patch —
  it's a newer UI generation with extra API surface.
- The Wi-Fi passphrase is exposed in cleartext in **two** places on the 5599
  (`/api/v2/home` and `/api/v1/deviceInfo`), same as the 5598's `/api/v2/home`.

## MLO

This particular 5599's firmware does **not** support MLO on the Wi-Fi
backhaul (confirmed directly by the user, not derived from the HAR). That
lines up with what the captures show circumstantially:

- Neither `/api/v2/wireless/mlo/state` nor `/api/v2/wireless/mlo_supported`
  was ever called by the UI in either capture — on the 5598 (which has MLO),
  the mlo-settings page under `#/wifi/*/priv/advanced/mlo-settings` calls
  `mlo/state` directly; its absence here suggests that UI element/route isn't
  offered at all on this firmware.
- `/api/v1/wireless/ssid_status` and `/api/v4/easymesh/meshdevices` show
  backhaul as **separate per-band SSIDs** (a 5GHz `DELTA-350f44_BH` and a
  distinct 6GHz backhaul BSSID) rather than one link spanning multiple
  bands, which is the non-MLO way of doing mesh backhaul.

So on this firmware, `wifi_stats()`-style backhaul band handling and any
future MLO wrapper in `sagemcom5598.py` would need a feature check rather
than assuming every 5598/5599 exposes those endpoints.

## Not yet confirmed

`/api/v1/wan/ip/stats` still hasn't been exercised against the 5599 in any
capture so far — a direct call would settle whether it's unchanged or moved.
